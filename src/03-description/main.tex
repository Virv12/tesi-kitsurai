\section{Description}
\label{sec:architecture}

Rustikai stores users' data in a set of \emph{tables}, each identified by a
UUID~\cite{rfc9562}.
Every table contains key-value pairs, where both keys and values are
uninterpreted arrays of bytes.

A Rustikai system operates on a \emph{cluster} composed of a static (see
Section~\ref{subsec:limitations}) set of nodes; a \emph{node} corresponds to a
server that usually runs on a dedicated physical machine.

Each node may be temporarily unavailable due to failures or network partitions,
and the system is designed to be resilient to such events and to continue operating
as long as a sufficient number of nodes are available.
Each node can be assigned to an \emph{Availability Zone} (see
Section~\ref{subsec:availability-zones}).

\subsection{Tables}
\label{subsec:tables}

Each table is characterized by four parameters specified by the user at creation time:
\begin{itemize}
    \item \texttt{throughput} or $T$: the overall throughput, expressed as requests per second, to be granted
        to clients accessing the table (see Section~\ref{subsec:throughput-model}).
    \item $N$: the replication factor for each key-value pair.
    \item \texttt{read\_concern} or $R$: the minimum number of nodes that must
        successfully respond to a read request (see Section~\ref{subsec:consistency}).
    \item \texttt{write\_concern} or $W$: the minimum number of nodes
        that must successfully respond to a write request.
\end{itemize}

These must satisfy the constraints $R, W \in \{ 1, 2, \dots, N \}$ and $T > 0$.
%
The system computes automatically the following parameters:
\begin{itemize}
    \item \texttt{id}: a UUID identifying the table, generated at creation.
    \item \texttt{responsible\_nodes}: a list of $M$ nodes, possibly
        heterogeneous, on which the table's key-value pairs are distributed,
        chosen to guarantee replication and data availability.
    \item $s_i$: the throughput (requests per second) allocated for the table on each node $i$,
      where the total throughput $S = \sum s_i$ satisfies the constraint
      $S = T \cdot N$.
\end{itemize}

\subsection{Consistency and Client-Visible Semantics}
\label{subsec:consistency}

Our store is a best-effort, partition-tolerant key-value service with explicit
client-tunable quorums. We make two deliberate design choices:

\begin{itemize}
    \item \textbf{No replica reconciliation.}
        Item payloads receive \emph{no} server-side conflict resolution and
        \emph{no} catch-up to the latest value for restarting or recovering
        replicas.
        Replicas that miss a write may indefinitely retain a divergent value
        until a later client write updates them (this is known a limitation of
        the current prototype).
    \item \textbf{Multi-value reads.}
        Reads may return multiple distinct versions of the same key.
        The store does not attempt to infer a single ``latest'' value, this is
        left to the application.
\end{itemize}

\paragraph{Quorum parameters.}
We use lowercase $N, R, W$ for the number of replicas, read quorum, and write
quorum.
A write to key $k$ is considered \emph{committed} once any $W$ replicas
acknowledge persisting the value; the system does not subsequently propagate
that value to the remaining $N - W$ replicas.
A read for key $k$ completes once responses from any $R$ replicas are received.

\paragraph{Quorum intersection.}
If $R + W > N$, then any set of $R$ replicas intersects any set of $W$
replicas.
Consequently, every read that gathers $R$ replies contains \emph{at least one}
payload written by any previously completed write.
However, in the presence of concurrent or failed writes, multiple distinct
payloads can appear in the read result, and the store offers no mechanism to
determine which is the ``latest'' value.
This has to be handled at the application level (similarly to semantic
reconciliation of Dynamo~\cite{Dynamo2007}), for example adding to the payload
a version number or a time-stamp that allows the client to select the most
recent value.

\subsection{Availability Zones}
\label{subsec:availability-zones}

To improve fault tolerance and ensure continuous data accessibility, Rustikai
adopts a replication strategy based on \emph{Availability Zones} (AZs).
Each node within the cluster is associated with an Availability Zone
identifier, a symbolic label representing either a physical or a logical
grouping of nodes, such as distinct data centers, server racks, or virtual
clusters distributed across geographical regions.

During table creation, the system enforces a zone-aware placement policy that
guarantees every key-value pair is replicated on $N$ nodes belonging to $N$
distinct Availability Zones.
Consequently, no two replicas of the same item reside within the same zone.

This design minimizes the likelihood of correlated failures leading to data
unavailability and ensures that a table remains operational even in the event
of a complete zone outage.
As long as the number of available zones satisfies the quorum parameters $(R, W)$
defined for the table, Rustikai continues to serve read and write requests
using replicas from these zones.

\subsection{Throughput Throttling}
\label{subsec:throughput-throttling}

In a multi-tenant setting, Rustikai enforces predictable performance and fair
resource distribution through explicit \emph{throughput throttling} applied
\emph{per node and per table}.
Each node regulates admission against its locally allocated share $s_i$ of a
table's budget, preventing co-located workloads from interfering and ensuring
that no single table can monopolize local resources.

The regulator is throughput-based and converges to the configured average throughput on
each node, while permitting a short, bounded burst of \qty{100}{\milli\second}
to absorb micro-bursts.
Over longer intervals, the admitted throughput per node is bounded to $s_i$,
yielding table-level guarantees in aggregate without relying on a centralized
gate.
A request exceeding the local budget will wait until capacity is available
again.

This \emph{per-node, per-table} throttling improves scalability: admission
control is fully decentralized, avoids single-node bottlenecks, and naturally
scales with cluster size as additional nodes contribute independent capacity.

\subsection{Throughput Allocation Model}
\label{subsec:throughput-model}

Rustikai adopts a conservative, request-per-second based admission policy.
At table creation, the allocator assumes that \emph{all} requests issued by the
table may carry the \emph{maximum allowed payload size}, and evaluates
feasibility under this worst-case condition.
The maximum payload size is configurable system-wide, so
deployments can tune guarantees to their hardware capabilities.

This pessimistic approach ensures that, if a table is admitted, each node can
sustain the requested throughput even under worst-case scenarios.
To support sound admission tests, each node must be \emph{profiled} prior to
service: its sustained capacity in requests per second is measured using
payloads of maximum size and then used by the allocator as that node's
budget.

However, to ensure the validity of this model, storage devices must be
solid-state drives (SSDs) in order to provide sufficiently predictable
performance for the guaranteed rates.
Rotational HDDs are not a viable option due to their seek time and rotational
latency which cause high variance and long-tail stalls, invalidating the
constant-throughput abstraction required by the allocator.

\subsection{Client API}
\label{subsec:interface}

The system exposes the public API through a REST interface over HTTP\@.
Since every node maintains a copy of the metadata for all tables, the client
can send requests to any node in the cluster, which acts as a \emph{router} to
forward the request to the appropriate nodes.

\begin{itemize}
    \item \textbf{\texttt{table-create}}: The client provides four parameters:
        $T$, $N$, $R$, and $W$.
        The system allocates sufficient throughput across the nodes to satisfy
        the requested configuration, creates the table, and returns the
        generated \texttt{id} of the new table.
        If the requested parameters cannot be satisfied, for instance due to
        insufficient available throughput or an insufficient number of AZs to
        meet the desired replication factor, the operation fails and an error
        is returned.

    \item \textbf{\texttt{table-delete}}: The client sends the \texttt{id} of
        the table to be deleted.
        The system marks the table as deleted and frees the allocated
        resources.

    \item \textbf{\texttt{item-get}}: The client sends the \texttt{id} of the
        table and the \texttt{key} to be retrieved.
        The system forwards the request to the responsible nodes and waits for
        at least $R$ successful responses within a system-wide configurable
        timeout.
        If the operation succeeds, it returns a list of the values received
        from the nodes; otherwise, it returns an error and includes any values
        successfully collected.

    \item \textbf{\texttt{item-set}}: The client sends the \texttt{id} of the
        table, the \texttt{key}, and the \texttt{value} to be set.
        The system forwards the request to the responsible nodes and waits for
        at least $W$ successful responses within a system-wide configurable
        timeout.
        If the operation succeeds, it returns a success message; otherwise, it
        returns an error.

\end{itemize}
