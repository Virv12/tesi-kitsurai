\section{Experimental Results}
\label{sec:results}

Literature on benchmarks for databases and data store is extensive
and covers what measures to collect for various guarantee of consistency levels~\cite{ConsistencyOverview}.
As our database has no consistency guarantees, we focus our experimentation on latency and scalability.

Experimental data were collected using three machines:
\begin{itemize}
    \item Machine $M$: MacBook Pro with M1 and \SI{32}{\giga\byte} RAM, built-in storage, operating system macOS~26, file system \texttt{APFS};
    \item Machine $A$: Intel Core i7-8750H (6 cores, 12 threads with Hyper Threading, locked at \SI{2.2}{\giga\hertz}), \SI{16}{\giga\byte} DDR4 RAM, \SI{128}{\giga\byte} SATA3 SSD, operating system Arch Linux, kernel \texttt{6.17.1}, file system \texttt{btrfs};
    \item Machine $H$: Intel Core i5-12450H (4 E-cores and 4 P-Cores, 12 threads with Hyper Threading, E-Cores locked at \SI{1.5}{\giga\hertz} and P-Cores at \SI{2}{\giga\hertz}), \SI{16}{\giga\byte} DDR4 RAM, \SI{512}{\giga\byte} NVMe 4xPCIe3 SSD, operating system Arch Linux, kernel \texttt{6.17.1}, file system \texttt{XFS}.
\end{itemize}

The machines were connected via a gigabit Ethernet network with a latency of about \SI{0.3}{\milli\second} while under stress.
For these tests, we configured the system with a \SI{4}{\kilo\byte} max request size,
a value chosen to avoid saturating the network connection in most tests,
and which allowed us to measure the performance of CPU and disk.

A purpose-built program (\texttt{ktb}) was developed to stress the system using multiple connections.
We first recorded baseline values by having each machine stress itself in both \texttt{item-get} and \texttt{item-set} operations
on a table with throttling disabled (i.e., \texttt{item-set} to sufficiently high limit) and value sizes of \SI{4}{\kilo\byte}.

Table~\ref{tab:results-stress} presents the results, which allows us to rank the machine as follows: $2H \approx M \approx A$.
\texttt{item-get} operations at \SI{512}{\byte} have been reported when the \SI{4}{\kilo\byte} run saturated the gigabit connection.

The scalability and replication of the system were then evaluated.
Unless stated otherwise, The following tests were conducted by running \texttt{ktb} on machine $H$, considering only \texttt{item-set} operations.
\texttt{item-get} operations were excluded because the operating system caches file reads, making their results unrepresentative of true random-access disk performance.
Nevertheless, the measured req/s values for \texttt{item-get} operations are reported in Table~\ref{tab:results-stress}.

We configured the machines for either a uniform key distribution, where each machine's bandwidth parameter was set to the same sufficiently high value,
or with a proportional key distribution, where each machine's bandwidth was still set sufficiently high but proportional to its self-stress results.
In our setup, for simplicity, machines $M$ and $A$ were assigned the same value, while $H$ was configured with twice that amount.

\paragraph{Distribution}
To test the key distribution and scalability of the system, we used a table configured
with enough bandwidth to saturate the test case, $N=1$, $R=1$, and $W=1$.
This configuration distributes requests across peers according to the machines' bandwidth proportions.


In the uniform case, each machine receives one third of the requests.
Thus, the slowest machine will be the first one to limit the number of requests.
We can therefore expect the overall rate to be three times the minimum individual rate,
as the other two machines will receive the same rate of request as the slowest one.
In our setup, the slowest machine is $A$, which achieved \SI{4.8}{\kilo\hertz}, yielding and expected overall rate of \SI{14.4}{\kilo\hertz}.


In the proportional case, as long as the machine bandwidth was configured correctly, no single machine should become a bottleneck.
We can then expect the overall rate to be the sum of the individual machines.
In our setup, this corresponds to \SI{20.6}{\kilo\hertz}.


Testing shows that the system scales as expected, reaching \SI{13.2}{\kilo\hertz} (92\%) and \SI{17.0}{\kilo\hertz} (83\%) of the expected values.
The losses can in part be accounted for by the CPU overhead of running the test itself and the probabilistic nature of key distribution.

\paragraph{Replication}
To test the system replication, a table created with enough bandwidth to saturate the test case, $N=2$, $R=2$ and $W=2$ was used.
This configuration allows for reproducible performance ($N=R=W$) and was considered more interesting than the simpler $N=3$, $R=3$ and $W=3$ case.


In the uniform case, the slowest machine again limits the overall rate.
Due to replication, each machine receives $2/3$ of the client requests, as the key space is distributed twice.
Therefore, the expected overall rate is $3/2$ of the slowest machine rate, accounting for the remaining third that do not hit the slowest machine.
In our case the total expected overall rate is \SI{7.2}{\kilo\hertz}.


In the proportional case, our faster node $H$ receives a full copy of the table, while $M$ and $A$ each store half.
We can expect the overall rate to be the minimum between $H$'s rate and the sum of $M$ and $A$'s rates.
In our setup, $H$'s is faster than $M$ and $A$ combined, yielding an expected overall rate of \SI{9.8}{\kilo\hertz}.


Testing confirms that the system scales as predicted, achieving \SI{7.2}{\kilo\hertz} (100\%) and \SI{9.4}{\kilo\hertz} (96\%) of the expected values.
The losses can again be explained by the CPU overhead of running the test itself and the probabilistic nature of key distribution.

\paragraph{Real-Time}
The last test focused on evaluating the real-time properties of the system, simulating a concrete use case.
With a proportional bandwidth configuration matching the measured rates in the self stress,
a table $T_T$ was created with $N=3$, $R=3$, $W=3$ and a bandwidth of \SI{200}{\hertz}.
To represent external interference, another table $T_O$ was created with $N=2$, $R=2$, $W=2$
and bandwidth such that it would saturate the machines configured bandwidth.
To stress the system, two extra instances of \texttt{ktb} were executed on machines $A$ and $M$, both targeting $T_O$.
The reported data was collected from machine $H$'s \texttt{ktb} instance targeting $T_T$.

The system successfully isolated the target table $T_T$ from the outside noise, maintaining the allocated throughput of \SI{200}{\hertz}.
Reported in Table~\ref{tab:results-isolation} are the measured latencies when the target table received less than \SI{200}{\hertz},
both with and without external stress.
Overall, a slight increase in latency was observed, which is expected, as no explicit latency control mechanism is implemented.
