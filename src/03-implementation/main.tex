\subsection{\texttt{get} and \texttt{set} operations}
\label{subsec:get-set}

To read or write a key, the following steps are performed:
\begin{enumerate}
    \item The client connects to a node of its choice, which acts as a
        \emph{router}.
    \item The client sends the key and, in case of a write, the value to be
        stored.
    \item The router computes the \texttt{n} nodes responsible for that key
        (see Section~\ref{subsec:replication-ring}).
    \item The router sends the read or write request to the responsible nodes.
    \item The nodes respond with the requested value or confirm the write.
    \item The router aggregates the responses and returns the first \texttt{r}
        (or \texttt{w}) available results to the client.
\end{enumerate}

If fewer than \texttt{r} (or \texttt{w}) nodes respond successfully, the
operation fails and the client receives an error.

\subsection{Tables}
\label{subsec:tables}

Each table has four parameters specified by the user at creation time:
\begin{itemize}
    \item \texttt{bandwidth} or \texttt{b}: the total number of requests (\texttt{get} and \texttt{set}) that the system must guarantee for the table, expressed in requests per second.
    \item \texttt{n}: the replication factor for each key-value pair.
    \item \texttt{read\_concern} or \texttt{r}: the minimum number of nodes that must successfully respond to a read request.
    \item \texttt{write\_concern} or \texttt{w}: the minimum number of nodes that must successfully respond to a write request.
\end{itemize}

And another four parameters computed automatically:
\begin{itemize}
    \item \texttt{id}: a UUIDv7 identifying the table, generated at creation.
    \item $S$: the effective bandwidth of the table considering the replication effect, computed as $\displaystyle S = b \cdot n$.
    \item \texttt{responsible\_nodes}: the list of nodes on which the table's key-value pairs are distributed, chosen to guarantee replication and data availability.
    \item $s_i$: the bandwidth allocated by node $i$ for the table, such that $\displaystyle \sum s_i = S$.
\end{itemize}

Each table is managed by a set of nodes, called \emph{responsible nodes}, chosen to guarantee replication and data availability.
On each node, a table can be in one of three states: \emph{prepared}, \emph{created}, or \emph{deleted}.
Tables can only progress in state in the order: \emph{prepared} $\rightarrow$ \emph{created} $\rightarrow$ \emph{deleted}.
A table is \emph{prepared} when the requested bandwidth has been allocated, but it has not yet been created.
A table is considered \emph{created} when all responsible nodes consider it so; it is considered \emph{deleted} when at least one node marks it as such.
The state of a table is synchronized among nodes through the \emph{Gossip} protocol (see Section~\ref{subsec:gossip}).

\subsubsection{Creation and Deletion}
\label{subsubsec:creation-deletion}

To create a table, the following steps are performed:
\begin{enumerate}
    \item The client connects to a node of its choice (called the \emph{router}) and sends the table's parameters \texttt{b}, \texttt{n}, \texttt{r}, and \texttt{w}.
    \item The router generates an \texttt{id} for the table and computes the effective bandwidth $S = b \cdot n$ to account for replication.
    \item The router requests the available bandwidth for the new table from the other nodes, allocating up to $b$ on a single node, thus ensuring that the table is replicated exactly $n$ times.
    If a node is unavailable it is skipped, while a responding node marks the table as \emph{prepared}.
    \item Once sufficient bandwidth is obtained (at least $S$), the router defines the list of responsible nodes and their respective quotas $s_i$.
    \item The router asks the nodes that responded in step~3 to execute the \texttt{commit} of the table; on these nodes the table enters the \emph{created} state.
    \item If all \texttt{commit} requests succeed, the creation succeeds and the router returns the \texttt{id} of the new table to the client; otherwise, creation fails and the router returns an error.
\end{enumerate}

If a node receives a preparation request for a new table but does not receive a \texttt{commit} within a certain timeout, it will mark the table as \emph{deleted}.
This ensures that, in case of errors during creation, the table does not remain in an undefined state that would entail a loss of allocated bandwidth.

To delete a table, it is sufficient for a node to mark it as \emph{deleted}; subsequently, thanks to the \emph{Gossip} protocol (see Section~\ref{subsec:gossip}), the other nodes will synchronize and the table will be considered deleted by all.

\subsubsection{Metadata}
\label{subsubsec:metadata}

The database contains a special table, not accessible to users, identified by a UUIDv8 generated from the 16 bytes \texttt{kitsuraimetadata}.
This table contains the metadata of all tables created in the cluster, including their parameters and responsible nodes.
Thanks to this, every node can act as a router for \texttt{get} and \texttt{set} requests.
The metadata table, identified by a UUIDv8, cannot conflict with the UUIDv7 generated for user tables, since the version is encoded within a UUID\@.

\subsection{Gossip}
\label{subsec:gossip}

Each node in the cluster initiates a \emph{gossip} exchange with a randomly chosen peer every second.
During the exchange, the two nodes synchronize the metadata of \emph{created} and \emph{deleted} tables, but not those \emph{in preparation}.
If the same table is in different states on two nodes, the state representing greater progress prevails.
Using a Merkle tree~\cite{MerkleTree} allows nodes to quickly identify divergent tables and synchronize only those.
If the peer is unavailable, the exchange fails.
Gossip enables the system to reach metadata consistency among nodes even in the presence of offline nodes or network errors.
