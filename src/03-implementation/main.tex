%\section{Architecture}
%\label{sec:architecture}
%
%The database is organized into \emph{tables}, each identified by a version~7 UUID~\cite{rfc9562}.
%Every table contains key-value pairs, where both keys and values are byte arrays.
%
%A Kitsurai system operates on a \emph{cluster} composed of a static set of nodes, which may occasionally be unavailable.
%A \emph{node} corresponds to an instance of the program running on a physical or virtual machine.
%Each node can be tagged with a string identifying its \emph{Availability Zone} (see Section~\ref{subsec:availability-zones}).
%Every node maintains a copy of the metadata for all tables.
%
%\subsection{Interface}
%\label{subsec:interface}
%
%Four main operations are supported:
%\begin{itemize}
%    \item \texttt{create-table}: creates a new table with the specified parameters.
%    \item \texttt{delete-table}: deletes an existing table.
%    \item \texttt{get}: retrieves the value associated with a key in a table.
%    \item \texttt{set}: sets the value associated with a key in a table.
%\end{itemize}
%
%Any of these requests can be sent to a node chosen by the client, which acts as a \emph{router} to forward the request to the nodes responsible for the specified table.
%
%\subsection{Tables}
%\label{subsec:tables}
%
%Each table has four parameters specified by the user at creation time:
%\begin{itemize}
%    \item \texttt{bandwidth} or \texttt{b}: the total number of requests (\texttt{get} and \texttt{set}) that the system must guarantee for the table, expressed in requests per second.
%    \item \texttt{n}: the replication factor for each key-value pair.
%    \item \texttt{read\_concern} or \texttt{r}: the minimum number of nodes that must successfully respond to a read request.
%    \item \texttt{write\_concern} or \texttt{w}: the minimum number of nodes that must successfully respond to a write request.
%\end{itemize}
%
%And another four parameters computed automatically:
%\begin{itemize}
%    \item \texttt{id}: a UUIDv7 identifying the table, generated at creation.
%    \item $\Sigma$: the effective bandwidth of the table considering the replication effect, computed as $\displaystyle \Sigma = b \cdot n$.
%    \item \texttt{responsible\_nodes}: the list of nodes on which the table's key-value pairs are distributed, chosen to guarantee replication and data availability.
%    \item $b_i$: the bandwidth allocated by node $i$ for the table, such that $\displaystyle \sum b_i = \Sigma$.
%\end{itemize}
%
%Each table is managed by a set of nodes, called \emph{responsible nodes}, chosen to guarantee replication and data availability.
%On each node, a table can be in one of three states: \emph{prepared}, \emph{created}, or \emph{deleted}.
%Tables can only progress in state in the order: \emph{prepared} $\rightarrow$ \emph{created} $\rightarrow$ \emph{deleted}.
%A table is \emph{prepared} when the requested bandwidth has been allocated, but it has not yet been created.
%A table is considered \emph{created} when all responsible nodes consider it so; it is considered \emph{deleted} when at least one node marks it as such.
%The state of a table is synchronized among nodes through the \emph{Gossip} protocol (see Section~\ref{subsec:gossip}).
%
%\subsubsection{Creation and Deletion}
%\label{subsubsec:creation-deletion}
%
%To create a table, the following steps are performed:
%\begin{enumerate}
%    \item The client connects to a node of its choice (called the \emph{router}) and sends the table's parameters \texttt{b}, \texttt{n}, \texttt{r}, and \texttt{w}.
%    \item The router generates an \texttt{id} for the table and computes the effective bandwidth $\Sigma = b \cdot n$ to account for replication.
%    \item The router requests the available bandwidth for the new table from the other nodes, allocating up to $b$ on a single node, thus ensuring that the table is replicated exactly $n$ times.
%    If a node is unavailable it is skipped, while a responding node marks the table as \emph{prepared}.
%    \item Once sufficient bandwidth is obtained (at least $\Sigma$), the router defines the list of responsible nodes and their respective quotas $b_i$.
%    \item The router asks the nodes that responded in step~3 to execute the \texttt{commit} of the table; on these nodes the table enters the \emph{created} state.
%    \item If all \texttt{commit} requests succeed, the creation succeeds and the router returns the \texttt{id} of the new table to the client; otherwise, creation fails and the router returns an error.
%\end{enumerate}
%
%If a node receives a preparation request for a new table but does not receive a \texttt{commit} within a certain timeout, it will mark the table as \emph{deleted}.
%This ensures that, in case of errors during creation, the table does not remain in an undefined state that would entail a loss of allocated bandwidth.
%
%To delete a table, it is sufficient for a node to mark it as \emph{deleted}; subsequently, thanks to the \emph{Gossip} protocol (see Section~\ref{subsec:gossip}), the other nodes will synchronize and the table will be considered deleted by all.
%
%\subsubsection{Metadata}
%\label{subsubsec:metadata}
%
%The database contains a special table, not accessible to users, identified by a UUIDv8 generated from the 16 bytes \texttt{kitsuraimetadata}.
%This table contains the metadata of all tables created in the cluster, including their parameters and responsible nodes.
%Thanks to this, every node can act as a router for \texttt{get} and \texttt{set} requests.
%The metadata table, identified by a UUIDv8, cannot conflict with the UUIDv7 generated for user tables, since the version is encoded within a UUID\@.

%\subsection{Gossip}
%\label{subsec:gossip}
%
%Each node in the cluster initiates a \emph{gossip} exchange with a randomly chosen peer every second.
%During the exchange, the two nodes synchronize the metadata of \emph{created} and \emph{deleted} tables, but not those \emph{in preparation}.
%If the same table is in different states on two nodes, the state representing greater progress prevails.
%Using a Merkle tree~\cite{MerkleTree} allows nodes to quickly identify divergent tables and synchronize only those.
%If the peer is unavailable, the exchange fails.
%Gossip enables the system to reach metadata consistency among nodes even in the presence of offline nodes or network errors.
%
%\subsection{Replication Ring}
%\label{subsec:replication-ring}
%
%To ensure database availability, we want every key to be replicated across multiple nodes while satisfying the following requirements:
%
%\begin{itemize}
%    \item Each key is replicated on \texttt{n} distinct nodes among those responsible for the table, to guarantee availability and tolerate up to $n-1$ node failures.
%    \item The bandwidth allocated to a table must be proportionally balanced among the nodes responsible for it.
%\end{itemize}
%
%To define the ring we require the values $b_i$ to be integers.
%If greater precision is needed when expressing the allocated bandwidth, a smaller unit (e.g., requests per millisecond) can be used, and the $b_i$ values can be multiplied by a scaling factor, e.g., 1000, to obtain integer values.
%The \emph{replication ring} is a circular array of size $\Sigma$.
%For each position in the ring we assign a node $i$ such that:
%
%\begin{itemize}
%    \item Every interval of length $n$ in the ring contains distinct nodes.
%    \item Each node $i$ occupies exactly $b_i$ positions in the ring.
%\end{itemize}
%
%Given a key, we compute its hash (using \texttt{XXH3}\footnote{\url{https://xxhash.com}}, a fast non-cryptographic hash algorithm) and find the corresponding position in the ring.
%The key is assigned to the \texttt{n} nodes immediately following the calculated position.
%If the properties of the ring are satisfied, the availability and bandwidth balancing requirements are met.
%

%\subsubsection{Existence conditions}
%\label{subsubsec:existence-conditions}
%
%As shown, if each node satisfies the condition $b_i \leq b$ (as guaranteed during table creation), then the replication ring exists and can be constructed.
%
%Since the ring size is $\Sigma = b \cdot n$, we might try to build the ring even if a node has bandwidth $b < b_k \leq \Sigma$.
%However, under these conditions the ring cannot exist: it is not possible to assign keys so that they simultaneously satisfy the replication and bandwidth constraints.
%
%For contradiction, suppose a node $k$ has bandwidth $b_k > b$.
%Then that node would contain $\displaystyle n \cdot \frac{b_k}{\Sigma} = \frac{b_k}{b} > 1$ of the total keys, which is absurd.
%
%This shows that the conditions imposed during table creation are \emph{necessary and sufficient} for the correct operation of the system.

%\subsection{\texttt{get} and \texttt{set} operations}
%\label{subsec:get-set}
%
%To read or write a key, the following steps are performed:
%\begin{enumerate}
%    \item The client connects to a node of its choice (the \emph{router}) and sends the key and the value (in case of a write).
%    \item The router computes the hash of the key and determines the \texttt{n} responsible nodes for that key.
%    \item The router sends the read or write request to the responsible nodes.
%    \item The nodes respond with the requested value or confirm the write.
%    \item The router aggregates the responses and returns the first \texttt{r} (or \texttt{w}) available results to the client.
%\end{enumerate}
%
%If fewer than \texttt{r} (or \texttt{w}) nodes respond successfully, the operation fails and the client receives an error.

%\subsubsection{Consistency model}
%\label{subsubsec:consistency-model}
%
%The system does not guarantee any form of consistency: there is no synchronization mechanism among nodes.
%If a write does not reach a node because it is unavailable, that node will continue to return the previous value until it receives a new write.
%
%Consistency guarantees can be strengthened by using the condition $r + w > n$.
%In that case, at least one node involved in the read will have received the latest write, thus ensuring more consistent reads.
%However, it is the client's responsibility to determine which of the returned values is the most recent, since the system does not provide timestamps or version identifiers.

%\subsection{Bandwidth allocation}
%\label{subsec:bandwidth-allocation}
%
%For bandwidth allocation, Kitsurai adopts a very simple model: it assumes that the maximum number of operations per second a machine can execute is fixed and independent of other factors such as the size of ongoing reads and writes.
%
%For this reason, each node only needs to know its maximum bandwidth---measured beforehand using standard profiling and sizing operations---to determine whether it is able to handle the load requested by a table.
